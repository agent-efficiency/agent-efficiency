Keep agent work focused. Make checks visible.

Agent Efficiency helps developers and engineering teams get verifiable work from Claude Code, Codex, and Cursor. It spots repeated work, adds relevant project notes, and records checks against the code they tested.

Use it to see where a session gets stuck and whether a passing result still applies when you review the change.

Practical help during the task

Spot repeated work while it is happening

Repeated failures, broad searches, and repeated installs can consume a session without resolving the task. Agent Efficiency recognizes these patterns and adds a short note that asks the agent to reconsider its next step.

Value for you: a way to flag unproductive activity without watching every tool call.

Advice is capped at 3 notes per turn and 8 per session. You can observe silently or turn it off.

Know which checks still apply

A test result matters most when it matches the code you are reviewing. Run a configured check and Agent Efficiency saves a verification receipt: a record of the result and the code state it checked.

If the code changes, the earlier pass becomes stale. With project consent, guard mode can ask the agent once to run a required check before it finishes.

Value for you: a clear distinction between a current pass and a result from an earlier version of the work.

See how verification works

Reuse project knowledge in new sessions

Keep test instructions, project conventions, and lessons from earlier work in a vault, a Git repository of short notes. Agent Efficiency selects notes that match the working folder and adds them to the session.

Value for you: relevant project knowledge can follow the work across sessions, with less need to paste the same instructions again.

You maintain the notes. Delivered context has a fixed allowance of 9,000 characters. A vault error does not block the session.

Find out whether it helps your team

Activity reports show calls, failures, guidance, and verification state. The experiment ledger compares similar tasks with silent observation and active advice.

Judge the cost of reaching an accepted result, including failed attempts and review effort. Model cost is included when the host supplies it.

Read the measurement approach

Make the decision with evidence

  • Did the work meet your standard?Record acceptance and the evidence supporting it.
  • Did repeated work or review effort change?Compare failures, actions, elapsed time, and human review.
  • Was the advice worth its overhead?Rate the guidance and inspect the time and context it adds.

Savings depend on your tasks and workflow. This release provides the tools to measure them; this guide makes no quantified savings claim.

You control how much it does

Start quietly
Observe records activity without adding advice. Advise adds short notes. Guard can request a missing required check with project consent. Off disables normal session recording and guidance.
Keep records local
The plugin stores activity counts, states, and check receipts on your machine. Its database excludes prompts, code, raw commands, and output. The monitoring process makes no model calls or network requests. Your agent and configured check commands retain their own behavior.
Use your chosen host
The plugin supports Claude Code, Codex, and Cursor. Setup and supported events differ by host. In version 0.2.2, Cursor uses a local plugin folder. Compare host support.
Inspect and adapt
The code is available under the MIT License. You choose the project’s checks, maintain its notes, and can inspect the rules behind the advice.

Try it on one project

Start with a repository and task type your team knows well. Set a clear acceptance standard so you can judge whether to adopt the plugin.

  1. Install and observe

    Follow the host’s setup guide, confirm the plugin is active, and collect a baseline with observation mode.

  2. Add checks and useful notes

    Configure the tests that support your review. Add a small set of project notes. Enable advice on comparable tasks.

  3. Review the results

    Compare acceptance, repeated work, and review effort. Keep useful guidance and revise what distracts.

How Agent Efficiency works

Agent Efficiency is a local plugin for Claude Code, Codex, and Cursor. It watches session events, gives short guidance from fixed rules, and records whether configured checks passed for the current code.

It runs when a host calls a hook or you use its terminal command. The monitoring path uses the Python standard library and SQLite. It makes no model calls or network requests.

The whole system

A hook is a local command the coding-agent application runs when something happens, such as a tool call or the end of a turn. An adapter translates each host’s event format into the shared runtime’s format. The same runtime then handles counting, guidance, verification state, and optional vault context.

Session
A conversation in a coding-agent host.
Turn
One user prompt and the work the agent performs before stopping.
Receipt
A structured record of an operation or decision. Verification receipts record check results; vault receipts record context-delivery decisions.

Source: architecture and hook dispatcher.

Events become a session history

At session start, the runtime records the session and pins a guidance pack. A pack is a local, versioned set of guidance cards. Pinning its digest, a hash used to identify its contents, keeps the session on the same cards even if another pack becomes available.

Several reports can describe one invocation

Schema 8 separates “a tool was called” from “its result was resolved.” A pre-tool event, a result event, and a later batch report can all refer to the same call. Matching reports update the same accounting result. When the host provides a call identifier, the runtime uses its digest to keep identical calls distinct.

Without a host call identifier, matching falls back to action fingerprints and separate success/failure handling. Accounting depends on the events the host actually supplies. Historical counts are not recalculated by the schema 8 migration.

Guidance is selected by rules

The runtime classifies the task and tool activity locally. Fixed policies look for signals such as repeated actions, repeated failures, broad searches, repeated installs, or a code edit followed by a stop without observed validation. Task guidance cards add short instructions for substantial build, research, and review work.

The renderer checks what the host supports at that event. It can add context, notify, or ask for a bounded continuation. An unsupported effect falls back to a supported response or no response. A monitoring error lets the coding agent continue.

ModeWhat happensVault context
offNo normal lifecycle telemetry or guidance. Hooks still recognize exact control messages.Not read or added.
observeRecords facts and silent guidance selections. Adds no guidance.Selected and counted, not added.
advise
Default		Adds short guidance. It can ask for validation when an edited turn stops without an observed check.Added on supported events.
guardUses configured required checks and current receipts when deciding whether to request a continuation.Added on supported events.

Guidance has a budget. A policy note appears at most once per turn, with a combined advice limit of 3 messages per turn and 8 per session. Vault context has a separate allowance. These bounds limit added context; they do not establish a cost saving.

Guard needs project consent

The repository must set mode = "guard" in agent-efficiency.toml and define a check required for code changes. When an edited turn stops, an applicable required check without a current passing receipt can trigger one request to continue and run the exact check command. The host must support continuation, and the continuation limit must still permit it.

Guard does not run the check itself. It does not guarantee that the agent follows the request or that the configured checks fully cover the task.

Source: modes, effect rendering, and stop handling.

A receipt ties a check to the code

Seeing a test command in a session is an activity signal. A verification receipt is stronger evidence: Agent Efficiency ran a configured command and recorded its result against a known workspace state.

What is bound to the receipt

  • The full Git commit.
  • Tracked changes and relevant untracked file content.
  • The project’s verification configuration and check identity.
  • The result, exit status, and completion time.

What each run can return

  • pass: exit 0 and unchanged, readable state.
  • fail: a nonzero command exit status.
  • blocked: timeout or failure to start.
  • inconclusive: state is unreadable or changed during the check.
A minimal configured check

This goes in agent-efficiency.toml at the root of a Git repository. The command is an array of arguments. Use the test command that applies to your project.

version = 1
mode = "advise"

[[checks]]
id = "unit"
command = ["python", "-m", "unittest", "discover", "-s", "tests"]
applies_to = ["**/*.py"]
required_for = ["code"]
timeout_seconds = 300
agent-efficiency check unit
agent-efficiency evidence list

The check’s output streams to the terminal and is not stored. The configured command can have its own side effects, permissions, or network access. It is not sandboxed by the receipt system.

Ignored files and contents inside the recognized tool-cache directories are excluded from workspace tracking under the documented rules. A current receipt establishes the configured check’s result, not complete task acceptance or an absence of defects.

Source: verification guide, check runner, and receipt freshness.

Vault context is a separate channel

A vault is a local Git repository of notes you maintain. Registered vault trees have indexes. Selection matches the current project using paths, repository metadata, and branches. The selector reads local metadata without starting Git or opening note bodies.

Rendering places a matched project note first, then short summaries of other active notes that fit. The whole rendered context has a 9,000-character allowance, separate from the advice budget. Resume delivery occurs only when the rendered text changed. An explicit vault request reselects the notes.

After compaction, Claude Code and Codex receive replacement context at the compact session-start event. Cursor receives it at the next successful tool result. A receipt transaction prevents two racing events from claiming the same pending delivery. A vault failure lets the session continue without that context.

Source: vault guide, context preparation, and delivery.

What the local database stores

The hook may inspect input content in memory to classify it. The database keeps controlled facts and digests rather than the original prompt, command, code, or output. A digest helps compare values without storing their source text; it is not a guarantee of anonymity.

In the database

  • Session and turn state; host and model names.
  • Project folder names and project keys.
  • Action classes, fingerprints, counts, and durations.
  • Guidance decisions, ratings, and bounded outcomes.
  • Verification and vault decision receipts.
  • Cost and token totals when the host supplies them.

Not in the database

  • Prompt text, source code, or patches.
  • Raw commands, tool output, or check output.
  • Assistant messages, transcripts, or environment values.
  • Vault note text, note IDs, titles, or summaries.
  • Vault paths, remotes, or branches.
  • Experiment evidence content or its location.

One shared data folder

The terminal command and all hosts resolve the folder in this order: --data-dir, then AGENT_EFFICIENCY_DATA, then $XDG_DATA_HOME/agent-efficiency, then ~/.local/share/agent-efficiency.

SQLite transactions protect updates from concurrent hook processes. Newly created data directories use owner-only access, as do new data files. Existing directories keep their permissions; doctor reports readable or shared entries.

Metadata still matters. Folder names, model names, timestamps, and counts can reveal details about work. The store is local operational data, not an anonymous public dataset.

Measure the cost of an accepted result

Fewer tool calls or less context can be useful signals. They do not prove that a task became cheaper or better. The project’s target is the total cost of reaching a verified, accepted result, including failed work and the cost of the monitoring itself.

The experiment ledger can compare observe and advise cohorts, meaning groups of comparable sessions assigned to those modes. Comparisons match task class, project key, task-set digest, host, model, and agent profile. Accepted outcomes need an explicit evidence type and digest.

Enrollment, ratings, and outcomes are retained. Exclusions get explicit reasons. Failed and abandoned work must not disappear from the cost of the comparison. Observed differences are not proof of causation.

What this guide establishes: how the released implementation works. It does not establish reduced cost, better acceptance rates, or successful activation in a particular live host.

Source: measurement protocol and report definitions. The separate vault experiment work is not part of this release.

Within an active session, exact control messages such as $agent-efficiency observe, $agent-efficiency on, and $agent-efficiency off change that session’s mode. They are ordinary chat messages. on selects advise; project guard consent can make the effective mode guard.

Version 0.2.2 uses schema 8. Older runtimes cannot open an upgraded database. Update the terminal command and every active host copy together. Stop writers, keep a complete backup, rehearse on a copy, then verify the installed versions and new host sessions. Follow the upgrade and rollback guide.

Doctor’s matching schema check is a compatibility check. It does not prove identical builds or live hook activation. A normal CLI invocation may initialize the selected data folder; it is not a substitute for the controlled upgrade procedure.

Design proposal · For discussionNot implemented in 0.2.2

The improvement flywheel

Notice opportunities as the product is used. Surface a clear Agent Efficiency suggestion. Let the user choose whether to use it, then learn from the result.

The aim is fewer total tokens to a verified, accepted result, with the requested scope, required checks, and quality of the work preserved.

The flywheelWhat the user seesUser choicesProving valueDecisions and open details

Each completed task can improve the next one

New guidance appears at a relevant moment during normal use. It identifies Agent Efficiency as the source, explains the proposed change, and waits for the user’s choice. Ignoring a suggestion leaves behavior unchanged.

Agreed direction: suggestions surface as the product is used, with enough context to decide. The user chooses which ones to use. A successful result can support a recommendation, but cannot activate new guidance automatically.

Select a stage to see its input, action, and evidence. All stages are included when you print.

1. Notice a relevant opportunity

Input
The current task, saved project notes, explicit corrections, and observed activity.
Action
Look for a specific opportunity, such as repeated broad searches where a saved note names the relevant component. Check scope and freshness. Activity counts alone do not prove that the work was unnecessary.
Evidence
Keep the source of the suggestion clear: a saved note, an explicit correction, or a measured pattern. Store only digests and fixed reason codes in the measurement database.

2. Prepare a clear suggestion

Input
A possible improvement and the facts supporting it.
Action
Prepare a short proposed action, its reason, scope, expected benefit, and limits. The existing agent may draft it within the enabled learning workflow; local hooks do not call a model. Deduplicate it against adopted and rejected guidance.
Evidence
Keep the candidate inactive in the user-controlled note store. Record drafting overhead. A hypothesis is labeled as a hypothesis, with no invented token-savings estimate.

3. Surface it and let the user choose

Input
A relevant candidate with enough context for a decision.
Action
Show an “Agent Efficiency suggestion” in a visible host surface at a natural decision point. Offer use once, use for similar tasks, not now, and do not suggest again. No option is selected in advance. Silence means no change.
Evidence
Record the explicit choice separately from the fact that the proposal was supplied. A hidden context injection does not count as showing a suggestion to the user.

4. Use only the chosen guidance and verify

Input
The user’s choice, its scope, and the unchanged task requirements.
Action
Use-once guidance expires with this task. Adopted guidance can be reused for matching tasks in the stated project. For the first slice, supply at most one learned tip per task, capped at 500 characters within the vault allowance. All required checks still apply.
Evidence
Record what guidance was supplied, available usage, current check receipts, and task acceptance. Choosing a tip does not establish that the agent followed it or that the task succeeded.

5. Evaluate the result and its cost

Input
The choice, task outcome, feedback, and available host usage.
Action
Include proposal text, drafting, applied guidance, retries, and failed work. Report everyday usage as observation. Use a separate, explicitly enabled comparison to estimate whether a tip helps similar tasks.
Evidence
Keep user adoption, task acceptance, and measured effectiveness separate. Missing token totals stay unknown. Users choosing a tip on easier tasks cannot establish its savings.

6. Refine suggestions and remember choices

Input
Outcomes and the user’s decisions about guidance.
Action
Reuse adopted guidance within scope, defer a not-now response, and suppress rejected suggestions. New wording that changes the action or scope returns as a new visible proposal. Good results never activate a new rule on their own.
Evidence
Retain versions, choices, and failed attempts. Do not evade a rejection with cosmetic wording changes. If adopted guidance becomes stale or harmful, stop using it and explain why.

Make the source and proposed change clear

Every proposal is labeled Agent Efficiency suggestion. It says why it appeared, what would change, where it applies, and what is still uncertain. The user should be able to decide from that notice.

The user decides what becomes guidance

Surface a useful proposal at the moment it can help, such as a pause after repeated unsuccessful work or the start of a matching task. Keep it separate from the agent’s own plan and from any error or required check.

Proposed frequency limit: at most one new suggestion per task, with no repeat during that task after deferral or silence. Adoption stays reversible. If a previously adopted tip becomes stale or harmful, pause its use and show an Agent Efficiency notice explaining the reason.

Learning can draft and rank suggestions automatically within the enabled scope. It cannot adopt them for the user. A suggestion’s source, the user’s choice, and its measured effect remain separate records.

The system binds the user’s choice to the exact suggestion and scope shown. The agent cannot approve its own suggestion. An unclear reply leaves it pending until the user’s intent is clear.

Separate a proposal from an instruction

What stays in the note store

Human-readable lessons, conditions, source references, adoption scope, and old versions. These are inspectable files under the user’s control. Private notes are not shared automatically.

What reaches the ledger

Guidance digests, fixed choice codes, proposal and delivery counts, context size, timing, available host usage, check evidence, and task acceptance. No note text, note titles, paths, prompts, code, or raw output.

The existing formats cannot yet express every part of this design. Adoption scope needs a versioned note format. User choices and version-linked outcomes need an explicit ledger migration. Host adapters need a tested visible proposal-and-reply path. If a host cannot show the notice, keep the candidate pending; do not silently inject it as guidance.

Prove that the loop pays for its context

During ordinary use, record choices and outcomes without claiming causation. People may accept suggestions on easier tasks or decline them for unrelated reasons. Adoption is a product decision, not evidence that a tip saves tokens.

For a controlled comparison, get explicit agreement to test an optional tip on matched tasks. Use the same normal guidance and required checks in both groups. Change only whether that tip is supplied. Do not silently withhold adopted guidance to create a baseline. Comparing all of observe with all of advise would mix this effect with the rest of the product.

For the first pilot, one task is one fresh enrolled session with a fixed brief, including its correction turns through acceptance or abandonment. Do not mix several unrelated tasks into that session.

Total observed tokens for the comparison group, including failed work and learning overhead, divided by verified accepted tasks.

  1. Assign before work. Use fresh sessions and matched tasks from a fixed task set. Keep host, model, effort, repository state, and task class comparable. Allocate the note before the first task turn.
  2. Freeze the trial. Pin the note text and selection rules until the comparison ends. Do not use a task’s own outcome to improve its treatment halfway through the trial.
  3. Count the whole cost. Include the visible proposal, guidance tokens, body reads, drafting and revision work, retries, and failed or abandoned attempts. Assign shared overhead to the relevant group, including suggestions that were not accepted.
  4. Check quality first. Acceptance and required verification must hold. Review time and defects remain visible. Never reward skipping work the user asked for.
  5. Keep uncertainty visible. If host token totals are missing, report context size and observed actions only. Useful feedback supports a hypothesis; it is not a token-savings measurement.

Proposed first pilot: 12 matched task pairs in one repository and host, with fresh sessions for each run and explicit trial consent. Keep the version fixed, retain every outcome, and review the individual failures. The sample size and meaningful benefit threshold remain discussion points. No threshold activates guidance without the user’s choice.

Optional comparisons can test whether older guidance remains useful. Expired, rejected, and out-of-scope notes never return through this process. Explicit user instructions and required project rules apply in both groups.

Use Ambara as a reference

Ambara already has compact context, deferred full reads, duplicate suppression, local feedback, and reviewed durable knowledge. These are useful design patterns for this loop.

Reference patternProposed use here
Compact entries firstSelect one short action for the current task. Open the full source only when needed.
Useful, noisy, stale, or duplicate feedbackUse feedback to inform scope, suppression, and review. Keep user preference separate from measured effectiveness.
Reviewable durable knowledgeKeep new suggestions inactive until the user chooses, retain version history, and ask again before changing meaning or scope.
Separate decisions from writesMake selection and evaluation deterministic functions. Keep file writes and optional agent drafting outside lifecycle decisions.

Recommendation: implement the small selection and evaluation pieces with Agent Efficiency’s existing Python standard-library runtime. Keep the current note store as the first source. This design adds no Ambara dependency and copies no Ambara source code. A future adapter could read Ambara context if users already keep their knowledge there.

Ambara’s context-payload estimates describe its own output. They should not be imported as proof of a reduction in the whole task’s tokens.

Reference snapshot: Ambara commit d8deed6, including its context and feedback interface, separate decision and write paths, and package boundary decision. Agent Efficiency’s current vault and measurement protocol are the starting points.

Build the first complete loop narrowly

  1. Surface one clear suggestion

    Use existing notes and observed activity for one recurring task type. Show the Agent Efficiency label, reason, proposed action, scope, and explicit choices.

  2. Honor the choice

    Implement use once, scoped adoption, deferral, and rejection. Confirm the selected effect. Verify that silence changes nothing and adopted guidance is not repeatedly re-approved.

  3. Learn from actual use

    Connect choices to task outcomes and available usage. Improve later proposals. Add opted-in comparisons for savings claims, and broaden candidate generation after this complete path works.

The first useful deliverable should complete this cycle for one note. A larger memory store, team synchronization, new model service, and automatic rewriting of all guidance are outside that first slice.

Decisions made and details still open

  1. Settled: the user chooses new guidance

    Suggestions surface during use and are clearly attributed to Agent Efficiency. They explain what they are, why they appeared, and what accepting them would change. The user decides. No response leaves behavior unchanged.

  2. Detail to settle: timing and repetition

    Proposed default: one new suggestion per task, at a relevant decision point. Defer until a later matching task after “Not now”; suppress after “Don’t suggest again.” The exact cooldown and each host’s visible presentation still need design.

  3. Detail to settle: evidence for recommendations

    Start with existing notes and explicit corrections. Preserve acceptance and verification, then compare total tokens and review effort in opted-in trials. Agree on sample size and a meaningful reduction before making savings claims. Evidence informs the user’s choice; it does not replace it.
